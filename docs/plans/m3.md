# M3 plan: big-file 3D

Status: proposed 2026-10-26. Scope from `../spec/01-spec.md` §10, as amended below: the mesh
pipeline (normalize, validate, proxy, thumbnail, 3D Tiles) and a 3D viewer. Decisions D-M3-1 to
D-M3-4 were the user's before spike S1; D-M3-5 to D-M3-9 follow from its results.

## Where M2 left us

Already done, and not repeated here: GLB classification and header extraction (`mesh:` counts
and extent from the JSON chunk alone, ING-6), the derive stage with its outbox, recipes rendered
in a sandboxed child process with memory, time and file-size limits (ING-7, ING-8, ING-11 to
ING-13), STAC assets with audited read URLs (ACC-8), and the tiler service, which serves one
item's tiles under a short-lived token the API mints in an audited request (ACC-9, ACC-5).

What M3 has to build:

- **Nothing derives from a mesh.** No recipe applies to `mesh`, so a GLB is cataloged and
  downloadable but never viewable.
- **Only GLB is read.** OBJ, PLY and glTF are classified by extension and get no metadata; FBX
  is not recognized at all.
- **The derive stage writes one file per asset.** A tileset is a JSON file and thousands of
  tiles.

## Spike S1: mago-3d-tiler failed

Run 2026-10-26 on mago-3d-tiler 1.16.3 (the stack's choice) with a realistic textured mesh:
West Maui to Haleakala from Copernicus GLO-90 heights upsampled elevenfold, draped with
Sentinel-2 imagery; 54M vertices and 108M triangles, 3.03 GB, also split into 192 nodes, and
the same at 0.9 and 1.6 GB. (The corpus's `stress-3gib.glb` puts 268M vertices on three points:
right for ingest, useless for tiling.)

| Input | Result | Peak memory | Output |
|---|---|---|---|
| 0.9 GB, 192 nodes, `-sbn` | ok in 3 min 25 s | 11.1 GiB (10 GiB heap) | 3.9 GB, 768 tiles |
| 0.9 GB, heap 4 or 6 GiB | exit 1, "root node children is null or empty" | 7–9 GiB | none |
| 1.6 GB, 3.0 GB | killed for memory while loading, under 13 and 15 GiB caps | 13–15 GiB | none |
| 29 MB, `-pg` (photogrammetry) | stopped after 31 min, unfinished, on one thread | 2.5 GiB | none |

Every completed tileset validated clean and streamed in 3DTilesRendererJS, but:

- **No geometric levels of detail** outside the photogrammetry mode: a parent holds every
  triangle of its children and only its textures shrink, so the overview of the 0.9 GB model
  downloads 941 MiB, everything. That is not streaming.
- **The mode that does simplify is unusably slow**, and memory runs to 10–12 times the input.
- **A heap too small fails without saying so**: no OutOfMemoryError, a misleading message.
- Smaller: it ignores glTF's Y-up axis (`-rx 90` needed), refuses a read-only input directory,
  and treats a whole one-mesh GLB as one object.
- The spec's pass criterion named the wrong tool: validation is Cesium's
  `3d-tiles-validator`; `3d-tiles-tools` has no `validate` command.

**S1b, our own tiler (prototype, same day).** Streaming partition into an adaptive tree, then
levels of detail by vertex clustering, in numpy:

| Input | Time | Peak memory | Output |
|---|---|---|---|
| 3.03 GB, one mesh | 3 min 24 s | 572 MiB | 4.8 GB, 2,782 tiles, root 47k triangles; overview 2 MiB, close view 62 MiB |
| 29 MB | 1 s | 361 MiB | 11 tiles; overview 1.3 MiB, close view 19 MiB |

Clean under `3d-tiles-validator`, and it streams: the overview loads the root alone.

## Decisions

| # | Question | Decision | Why |
|---|----------|----------|-----|
| D-M3-1 | How do tiles reach the viewer? | **An item-scoped scene token checked by the tiler service**, minted by an audited `POST /items/{id}/scene`, as previews are (D-M2-1). ACC-8 is unchanged: no SAS for tilesets. | A tileset is thousands of requests; per-tile SAS URLs would mean signing each one, and auditing each would flood the log. |
| D-M3-2 | "Place on map"? | **Cut.** No user writes to items in M3. A mesh without a CRS has no footprint and is viewed on its own. Spec §8's Georeferencing row and §10's M3 row change. | Keeps items written only by the pipeline (one writer, ING-2); georeferencing is an editing feature, and items have no editing yet. |
| D-M3-3 | Mesh normalizers? | **glTF/GLB read directly; OBJ, FBX, PLY and STL through Assimp** (`assimp-py`, MIT, wheels bundling Assimp 6, BSD-3), in the sandbox, to our own in-memory mesh. IFC and USD deferred. | One converter covers the common interchange formats; IFC and USD each need a large toolkit for one format. |
| D-M3-4 | Scratch for big jobs? | **A bounded scratch per job, sized by size class**: the derive stage refuses a job whose original times the recipe's declared scratch factor exceeds its class's scratch; locally a volume, in cloud the node's ephemeral disk. | A crash can't fill a shared disk, and a job too big for its class fails as `over-budget`, visibly, instead of thrashing. |
| D-M3-5 | 3D Tiles from what? | **Our own tiler** (`worker/meshes/`): streams the mesh into an adaptive tree, writes leaves losslessly, and builds each parent by vertex clustering its children on a grid of its size over 256; that cell's diagonal is its geometric error. Pure numpy; memory bounded by chunk and tile, not by file. | S1. Vertex clustering is the out-of-core method (Lindstrom 2000): bounded memory, deterministic, and its error is exact. A quadric simplifier can replace it behind the same function if quality needs it. |
| D-M3-6 | One file or thousands? | **One `.3tz` per item** (3D Tiles archive: an uncompressed ZIP with a hash index), the `tileset` asset. The tiler service reads entries from it by range through the blob port. | ING-12's one asset per role and version holds as is; rebuilding (ING-7) replaces one blob; nothing lists or deletes thousands of blobs. |
| D-M3-7 | Proxy and thumbnail? | **From the same tree**: the proxy GLB is the coarsest level that fits 64k triangles; the thumbnail is that proxy drawn by a small numpy rasterizer (flat shading, base colour or texture). | No GPU, no headless browser, no Blender in the worker. |
| D-M3-8 | Validation? | **Our reader validates structure** (accessor bounds, index ranges, counts) before reading a byte of geometry, and refuses what fails as `unrenderable`. Tests run Khronos's glTF-Validator and Cesium's 3d-tiles-validator over our outputs. | The pipeline stays Python; the official validators check our writers, which is where a bug would be. |
| D-M3-9 | Size classes? | **S and M only.** A GLB is at most 4 GiB, inside M (< 5 GB), and the tiler's memory doesn't grow with the file, so M3 needs no L class. | L returns when something needs it (point clouds, M4). |

## New and changed invariants

- **ING-14 Tiles are faithful** (new): a tileset's leaves hold every triangle of the mesh once
  (none lost, none repeated, vertices exact to float32), every tile's content lies within its
  bounding volume, geometric error falls strictly toward the leaves, and every vertex of a
  coarser tile lies within its geometric error of the surface it stands for.
- **ACC-3** (derivatives, planned for M3): derivatives have no marking of their own; every
  byte path to one reads its item's, so a derivative's marking is its source's by
  construction. Status becomes enforced, with a test that a 3D tile is served only under the
  item's marking.
- **ACC-9** gains scene tokens and 3D tiles; **ACC-5** audits opening a scene, as previews.
- **ING-8** covers the tiler and Assimp: both run in the render sandbox.

## Slices

Each slice is one PR, ends with `make check`, and adds its mutants.

### 1. Plan, spec and the nightly

This document; spec §3 (mesh derive), §8 and §10 amended for D-M3-2, D-M3-5 and D-M3-6; stack
table and S1 row updated; ING-14 added. (The nightly's time-boxed soak and canary landed just
before, as their own PR.)

### 2 and 3. Reading meshes and the `tileset` recipe (ING-7, ING-8, ING-14)

- `worker/meshes/gltf.py`: a GLB's scene as primitives with world transforms, accessors read in
  bounded chunks with strides, components and normalization, validated first.
- `worker/meshes/model.py`: the in-memory mesh a tile holds (positions, normals, UVs, indices,
  per material), and the GLB writer.
- `worker/meshes/tiler.py`: partition, clustering, per-tile texture crops; `.3tz` writer.
- Property tests for ING-14 over random meshes; 3d-tiles-validator and glTF-Validator over a
  fixture tileset; a recipe test on the corpus GLBs.
- Scratch sizing per D-M3-4.
- Mutants: a clustered tile's error understated, a leaf losing its last partial chunk, a tile's
  bounding volume taken from its parent.

Done as one PR, with these changes from the above:

- **ING-14 says what the tests found it must:** a tile's box holds its children's as well as its
  content (3D Tiles culls a subtree by its root's box), and a coarse tile's error is its own
  clustering's plus its children's worst, which bounds its distance from the mesh at every level.
- **The validators run outside the pipeline,** as D-M3-8 planned, from their own npm package
  (`api/tools/validators`): the validator needs `sharp`'s native build, which stays out of the web
  app. CI requires them; locally `make services` installs them and their test skips without.
- **Size class M is the derive stage's limit now:** originals under 5 GB (was 2 GiB) and outputs
  up to 8 GiB, since a tileset is about 1.6 times its GLB. The per-class scratch check (D-M3-4)
  waits for the L class; until then one class bounds everything.
- **The production tiler matches the prototype:** the 3.03 GB S1 mesh tiles in 3 min 40 s at a
  peak of 340 MiB, into a 4.97 GB `.3tz` that validates clean.
- **The asset's role is `tileset`,** not `3dtiles`: the catalog's rule wants a role that starts
  with a letter, which only a test running the recipe through the derive stage into Postgres
  showed; that test now runs for meshes as it does for rasters. The tiler's fine grid also scales
  with the model (a cell per four triangles, up to the cap), so a small model renders in the
  sandbox's memory with room to spare.
- Mutants: `tile-error-ignores-children`, `partial-chunk-dropped`, `mesh-index-unchecked`,
  `tile-box-without-children`, `tileset-role-the-catalog-refuses`.

### 4. Scenes: token, proxy, routes (ACC-3, ACC-5, ACC-9)

- `POST /items/{id}/scene` (audited) mints a scene token for one readable item with a
  `tileset` asset; the tiler service serves `/scenes/{token}/{path}` from the `.3tz`'s index by
  range reads, with a per-process index cache.
- The catalog simulator gains scenes beside previews.
- Mutants as for previews: a token for any item, never expiring, unaudited.

Done, with these changes from the above:

- **Scene tokens are preview tokens for another audience** (`previews.SCENE_AUDIENCE`): one
  signing key and one verifier, and neither kind opens the other's routes. The API opens both
  through one function, so they're audited and refused alike.
- **The `.3tz` format lives in `ingest_api/tilesets.py`,** shared by the worker (writer) and the
  tiler (reader), as tokens are in `previews.py`. The reader trusts nothing in an archive: every
  offset and length is checked against its size and a cap, ZIP64 included (the 3 GB S1 tileset's
  index lies past 4 GiB). A tile costs a head and two range reads; an index is read once per
  archive version and kept, for 64 archives, per tiler process.
- **ACC-3 is enforced:** derivatives have no marking of their own and every path to one is opened
  only for its item's readers; a CUI mesh's scene is refused to an uncleared caller as the item is.
- Mutants: `scene-takes-a-preview-token`, `scene-of-the-original`; `preview-unaudited` now
  guards the one place both are audited.

### 5. 3D viewer

The item page gains a 3D view: three.js and 3DTilesRendererJS over the scene, orbit controls,
fit to the root's bounds; no base map, since meshes have no place on one (D-M3-2).

Done, with these changes from the above:

- **The view is a full-window layer** over the search, opened from an item's details ("View in
  3D") for items with a tileset, and closed with Escape; three.js loads only then (its own chunk).
- **Previews and scenes share one session hook** (`useTilerSession`), so both reopen before their
  tokens expire; the viewer swaps a renewed token into every later request.
- **nginx and Vite route `/scenes/` to the tiler,** as `/tiles/`: found by loading a scene
  through the stack, where the SPA answered instead.
- Checked in Chromium on the running stack, desktop and phone: a tileset made by the deriver from
  an upload streams, orbits and zooms.

### 6. Proxy and thumbnail

`proxy` (GLB) and `thumbnail` (PNG) recipes for meshes, per D-M3-7.

Done, with these changes from the above:

- **Not from the tree, from one streamed pass** (`meshes/coarse.py`): the whole model clustered
  on a grid as it's read, so a proxy or thumbnail doesn't wait on the tiler, and memory is the
  grid's occupied cells. Each has a triangle budget (64k for the proxy, 32k for the thumbnail):
  a model that fills its cells (a volume, or noise) is clustered coarser, in memory, until it
  fits, with texture bands as coarse as the grid so seams don't hold it back.
- **The thumbnail is drawn by `meshes/drawing.py`:** an orthographic view from above a corner, a
  depth buffer, two-sided Lambert shading, each triangle its material's colour times its texture
  at its centre; transparent around the model. A chess set of 20-odd materials draws in under
  3 s. It shares the `thumbnail` role with rasters', so search shows it the same way.
- **Risk found on the way:** GDAL reported TIFF write errors on a full disk without raising them;
  in the sandbox the file-size limit stops a render before then, but a full scratch volume
  would not. Scratch sizing (D-M3-4) is what keeps that from happening.

### 7. Normalizers

FBX classified by its magic; OBJ, FBX, PLY and STL through Assimp into the same model, so
every recipe above applies; their header extraction (counts, extent) through Assimp too, in the
extraction sandbox, under a size cap.

### 8. Close-out

Corpus: the mesh samples and a textured terrain built like S1's, with manifest expectations;
`make e2e`; the demo catalog gains meshes; `make soak` and `make mutants-full`; docs.

## Not in M3

Point clouds (COPC, 3D Tiles from LAS/LAZ) and the L size class move to M4, with PDAL. IFC and
USD normalizers (D-M3-3). Georeferencing a mesh (D-M3-2). `<model-viewer>` and USDZ stay in M4.

## Risks

- **Vertex clustering's look.** It can merge across thin features and smear UV seams at coarse
  levels. Mitigated by per-material clustering; a quadric simplifier is the fallback.
- **Textures.** A tile crops its texture to its UV extent; a model with UVs spread across many
  charts gets a whole-image texture per tile, scaled to 1024 px. Atlas repacking waits for a
  need.
- **Cracks between tiles at coarse levels**, up to one geometric error wide: sub-pixel when the
  renderer honours the error, visible if it doesn't.
